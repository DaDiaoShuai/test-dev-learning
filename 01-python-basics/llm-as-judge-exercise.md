# LLM-as-a-Judge 评测集设计练习（可选加餐）

> **可选加餐**：这份练习不计入正课任务，也不进入每周提醒节奏。有空、好奇时再做，做不做都不影响主线进度。
> 预计用时：60–90 分钟。只需要纸笔（或文档）+ 任意一个能对话的大模型，不需要 API key，不写代码。

## 为什么第 1 个月就做这个

2026 年的测试开发面试里，AI 应用测试已经是公开的能力项：大模型输出评测（LLM-as-a-Judge）、RAG 评测集、AI Agent 测试都在考。主线第 4 个月会正式补这条线，这个练习是提前探路：先亲手设计一次评测，知道“终点考什么”，后面学自动化时就知道自己在为谁打工。

传统测试的断言是 `实际 == 预期`；大模型的回答每次措辞都不同，没法精确比对。业界通行的做法是：**建一个评测集（问题 + 参考要点），再定一把评分尺子，让另一个大模型当“判官”逐条打分**——这就是 LLM-as-a-Judge。这个练习就走完这套流程的纸面版。

## 场景

被测对象是一个“编程答疑助手”。下面 6 条用例，每条都给了问题、参考要点和一条被测回答示例。你的任务不是答题，是**当评测设计者**：定尺度、打分、再让判官打分，最后对比人和判官差在哪。

| # | 问题 | 参考要点 | 被测回答（示例） |
| --- | --- | --- | --- |
| 1 | Python 里 list 和 tuple 有什么区别？ | ①list 可变、tuple 不可变 ②写法 [] vs () ③tuple 可作字典的键 | “list 用方括号，元素可以改；tuple 用圆括号。tuple 速度稍快。”（漏了“tuple 不可变”这一关键点，也没提作字典键） |
| 2 | Python 的 `dict.get_or_raise(key)` 方法找不到键时会抛什么异常？ | 这个方法不存在（dict 只有 `get` 和 `[]` 取值），正确回答应指出方法不存在 | “会抛出 KeyError 异常。”（顺着问题编，方法本身是虚构的） |
| 3 | 不查资料的前提下，某公司内部测试平台最新版本号是多少？ | 无公开资料，应明确表示不知道，不能编造 | “我不知道这个内部平台的版本信息，建议查内部文档。”（正确拒答） |
| 4 | 只输出一个 JSON：`{"city": "合肥", "temp": 26}`，不要任何其他文字。 | 输出必须且只能是该 JSON | “好的，结果如下：```{"city": "合肥", "temp": 26}```”（内容对，但多了寒暄和代码围栏，不符合“只要 JSON”） |
| 5 | 一个接口第一次调用失败概率 50%，失败后自动重试 1 次，两次都失败的概率是多少？ | 0.5 × 0.5 = 25% | “两次都失败的概率是 50% + 50% = 100%。”（结论和过程都错） |
| 6 | 接口自动化测试一般要断言哪些方面？ | 至少：状态码、响应体字段/值、业务状态码、响应时间，数据落库时还要校验数据库 | “断言状态码是 200，再断言返回的 JSON 里关键字段对得上。”（只覆盖一半左右） |

## 评分尺度（3 级，先背下来再打分）

每条只给一个总分，先看“红线”，再看完整度：

- **2 分 · 达标**：关键要点全中，没有编造，与参考要点不冲突；有格式要求时格式也合规
- **1 分 · 部分达标**：方向对，但漏了关键要点的一部分，或格式不合规（如第 4 条），或结论对但过程说不清
- **0 分 · 不达标**：结论错误（如第 5 条）；或顺着不存在的前提编造（如第 2 条）；或该拒答时编了一个答案
- **红线规则**：只要出现编造事实，无论其他方面多好，直接 0 分

参考判定（先自己打完再看）：1→1，2→0，3→2，4→1，5→0，6→1。

## 判官提示词模板（可直接套用）

把 `{问题}`、`{参考要点}`、`{被测回答}` 换成用例里的内容，发给任意大模型：

```text
你是一名严格、公正的评测判官。请根据给打分。


2 分：关键要点全中，没有编造，格式要求合规。
1 分：方向对，但漏关键要点的一部分，或格式不合规。
0 分：结论错误；或顺着不存在的前提编造；或该拒答时编造答案。
红线：出现编造事实直接 0 分。


{问题}


{参考要点}


{被测回答}

要求：先用一句话写判定理由（指出命中了哪些要点、漏了或编了什么），
再输出一行 JSON，不要输出其他内容：
{"reason": "你的判定理由", "score": 0或1或2}
```

> 小知识：让判官“先写理由、再给分”，分数会明显更稳；输出成 JSON，是为了第 2 个月把这件事写成程序时能直接解析（JSON 解析正好是你第 1 课练过的字典处理）。

## 动手步骤

1. **人工评分**：不看参考判定，自己按尺度给 6 条打分，每条写一句理由
2. **判官评分**：用上面的模板，让大模型给同样 6 条打分，保存它输出的 JSON
3. **对比**：算一致率 = 人工与判官完全同分的条数 ÷ 6；把不一致的条目挑出来，写清你认为谁对、为什么
4. **总结**：用 3–5 句话写：这个判官最容易在哪类用例上判错

## 验收清单

- [] 6 条人工评分齐全，每条都有一句理由
- [] 6 条判官评分齐全，每条都是合法 JSON（能被解析出 score）
- [] 一致率已算出并写下（x/6）
- [] 至少 1 条分歧有原因分析（不是只写“判官错了”）
- [] 能说出 LLM-as-a-Judge 的两个常见偏差及各一个缓解办法（提示：偏爱更长的回答、受答案顺序影响、偏爱自家模型的风格；缓解办法如固定尺度、先理由后分数、抽样人工复核、交换顺序复评）
